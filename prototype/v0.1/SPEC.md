# GPTFS 0.1.0 format specification

Status: experimental implemented profile, October 23, 2026. `gptfs.py` is the reference implementation. Normative requirements below describe this profile, not proposed future features. The container extension may be `.gpt` or `.GPT`; identify it by its SQLite header, application ID, and manifest, never by extension alone.

## 1. Design and physical representation

One SQLite 3 database. Header: `SQLite format 3\0`. `PRAGMA application_id = 0x47505446` (GPTF); `PRAGMA user_version = 1`. Default SQLite rollback-journal transactions are used; a transient `-journal` file can exist during a write. Distribute a closed, committed database. The physical file bytes need not be reproducible; logical object identities are reproducible.

Four tables are authoritative:

```sql
manifest(id INTEGER PRIMARY KEY CHECK(id=1), body BLOB NOT NULL)
blobs(id TEXT PRIMARY KEY, data BLOB NOT NULL)
objects(id TEXT PRIMARY KEY, body BLOB NOT NULL)
events(seq INTEGER PRIMARY KEY, id TEXT UNIQUE NOT NULL, body BLOB NOT NULL)
```

Every table has BEFORE UPDATE and BEFORE DELETE triggers that abort. The API exposes inserts only. The ledger is a single ordered history; there is no branching or merge operation. `BEGIN IMMEDIATE` serializes writers, verification runs before mutation, and related inserts commit in one transaction. SQLite locking waits up to five seconds. Multi-process stress and forced power-loss recovery are not validated here.

## 2. Canonical identity

`gptfs-json-1` is deliberately smaller than general JSON or RFC 8785:

- Allowed values: null, booleans, strings, arrays, objects, integers with absolute value at most 2^53−1. Floating-point values are forbidden.
- Object keys must be ASCII strings and sorted lexicographically. Array order is significant.
- Serialize compact JSON with comma and colon separators, no extra spaces, no final newline, and UTF-8 encoding. Escape JSON control characters, quote and backslash; preserve other Unicode characters directly. Python `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(',', ':'), allow_nan=False)` defines escaping in this implementation.
- Strings are not Unicode-normalized. Source bytes and line endings are not rewritten. Unpaired surrogates cannot be UTF-8 encoded.
- Metadata set-like arrays generated by the API (parents, intent object IDs, types, capabilities) are sorted and deduplicated.

All IDs are `sha256:` followed by 64 lowercase hex digits:

```text
blob_id   = sha256(raw bytes)
object_id = sha256(UTF8("GPTFS:object:1") + NUL + canonical(envelope))
event_id  = sha256(UTF8("GPTFS:event:1")  + NUL + canonical(event body))
```

Here `sha256(...)` denotes the prefixed textual ID. No ID is included in its own hashed body. Identical payload bytes deduplicate even when provenance differs. Object identity includes provenance; changing origin, type, or parents creates a new object. Event IDs include sequence, previous ID and timestamp, so separate ingests remain separate custody events even when their object IDs match.

## 3. Manifest

The singleton manifest contains:

| Field | Value / meaning |
|---|---|
| format | `GPTFS` |
| format_version | `0.1.0` |
| schema_version | integer `1` |
| project_id | random UUID string |
| name, owner | display name and local owner label |
| created_at | UTC ISO timestamp with microseconds |
| canonicalization | `gptfs-json-1` |
| hash | `sha256` |
| capability_ceiling | `["text.stats"]` |

The genesis event contains the manifest digest. Unknown application/schema/format versions are rejected. The manifest is not edited in place. A future incompatible migration must produce a new container with explicit source lineage; that migration is not implemented. Project names and owner labels are metadata, not registered identities.

## 4. Typed object envelope

```json
{
  "schema": 1,
  "type": "source",
  "blob": "sha256:<raw-byte digest>",
  "media_type": "text/plain; charset=utf-8",
  "size": 72,
  "origin": "sample:original-observation",
  "parents": [],
  "authority": "none",
  "trust": "untrusted"
}
```

Types: `source`, `reference`, `skill`, `note`, `evidence`, `plugin-manifest`, `bundle`. All except `bundle` require UTF-8 payload bytes. A bundle may carry opaque binary data. The importer uses `bundle` for undecodable binary members as well as the original ZIP; it does not interpret those bytes as executable files. The type is descriptive, not a grant of authority. `evidence` remains untrusted: verification may check a deterministic result without authenticating its author.

`parents` names existing objects at first custody insertion, making insertion-time lineage acyclic. It asserts derivation or containment; it does not prove that a human summary correctly follows from a source. `origin` is a required nonempty label, never a fetched URL or an execution target. No implicit source fetching occurs. Raw bytes are limited to 8 MiB per blob.

## 5. Event envelope and intent ledger

All events have `seq` (contiguous integer starting at 1), `previous` (prior event ID, null for genesis), `kind`, `actor` (local label), `at` (local clock UTC string), and `data`. The `events.id` column holds the body digest. Exported JSON adds this ID to the event object; remove that exported `id` field before hashing.

| Kind | Data fields and semantics |
|---|---|
| genesis | `manifest`: digest of canonical manifest; first event only |
| custody | `object`, `action: ingest`, `origin`; actor/time record local receipt into custody |
| intent | `text`, `objects`, `capabilities`, `types`, `max_bytes` |
| admission | `intent`, `object`, `rationale`, `code`, `decision`, `role: data`, `granted_authority: []` |
| execution | `intent`, `object`, `admission`, `capability`, `code`, `evidence`, `status`, `runner` |
| import | `adapter`, `bundle`, `files`, `plugin_name`, `authority_granted: []` |

The **intent ledger** is the ordered subset of events with kind `intent`, protected by the same chain. Text is the explicit task statement; the structured fields are the enforceable scope. No semantic inference from intent text widens that scope. Only the actor label equal to manifest.owner can create an intent through this API. This check is not user authentication.

Each intent is independent and remains usable; newer intents do not automatically revoke older ones. There is no edit, supersession, revocation, expiry, one-time-use or delegation operation in v0.1. Changing a task means adding a new intent with fresh receipts. Stronger lifecycle control is a next-release requirement.

## 6. Admission transition

Inputs: an earlier intent ID, an existing object ID, a nonempty caller rationale. Evaluate in this order:

1. Object absent from exact intent.objects → deny, `object-outside-intent`.
2. Object type absent from intent.types → deny, `type-not-allowed`.
3. Sum bytes of distinct allowed objects for this intent, including this candidate, exceeds max_bytes → deny, `context-budget-exceeded`.
4. Otherwise allow, `within-explicit-scope`.

Every well-formed request writes an admission receipt. Repeated admission of the same object does not double-charge the byte budget. Budget counts payload bytes, not tokens or JSON-envelope overhead. This is a logical data admission decision; v0.1 does not construct or send a model prompt. Skills can be explicitly admitted as data when their type is listed, but are never installed as system instructions. Granted authority is always empty.

## 7. Execution and evidence

Only `text.stats` is implemented. A runner request must name an earlier intent, exact object, and earlier allowed admission for that same pair. Requested capability must belong both to the implementation ceiling and to the intent. Failures record `capability-not-granted` or `valid-admission-required`, status `denied`, and null evidence. The denied request may name an unknown object; no payload is accessed in that case. Unknown intent IDs are validation errors rather than policy denials.

On success, the runner decodes the admitted payload as UTF-8 and records bytes, Unicode code-point count, whitespace-split word count, `splitlines()` line count, and the raw-content digest. This is a Python text measurement, not linguistic tokenization. The result is canonical JSON in a new evidence object whose parent is the measured object. An execution event points to that evidence with status `completed`, code `authorized`, runner `gptfs-text-stats/0.1.0`.

Evidence, its custody event and execution receipt commit together. The event timestamp records receipt creation, not an externally witnessed start/end interval. A crash rolls the transaction back; no attempt/failure receipt survives a pre-commit crash. The runner performs no shell, network, filesystem-output, or model side effects beyond writing this container and printing its response.

## 8. Claude .plugin adapter

An adapter accepts a ZIP containing exactly one `.claude-plugin/plugin.json`, at the archive root or below one common prefix. The manifest must decode as a JSON object with a nonempty string `name`. Other manifest fields are preserved without semantic validation. The adapter is not a complete Claude manifest validator.

- Retain the complete original ZIP as a bundle object.
- Import each file without extraction: manifest → plugin-manifest; `skills/**/SKILL.md` → skill; other UTF-8 files → reference; non-UTF-8 files → bundle.
- Store the original bundle as every imported member's parent. Record root-relative filename → object ID in an import receipt.
- Preserve hooks/scripts/configuration as bytes. Never start hooks, MCP servers, agents, or scripts. Never turn plugin metadata into intent or capabilities.
- Limit compressed bytes to 8 MiB, expanded bytes to 32 MiB, member bytes to 8 MiB, and entries (including directories) to 256.
- Reject absolute/traversal/backslash/colon/empty-component paths, path normalization, case-folded duplicate names, symlinks, encryption, multiple manifests, and files outside the plugin root. ZIP CRC checks occur during reading. Directories are not separate GPTFS objects but remain in the retained ZIP.

Custom component paths remain data; classification only recognizes the standard skills path. This is one-way import compatibility, not equivalent Claude execution behavior.

## 9. Verification and checkpoints

`verify` checks SQLite integrity, supported version, canonical bytes and hashes, blob sizes, known object types and fixed trust/authority, parent availability at custody insertion, contiguous event links, intent scopes, admission decisions, matching execution admissions, recomputed statistics, archive-to-member byte identity, and unlogged/orphan objects or blobs. Unsupported event kinds fail. This is a profile verifier, not a full JSON Schema implementation; extra metadata fields are not a general extension contract.

A checkpoint contains project_id, manifest digest, seq, and head event ID. Verification accepts later extensions if the checkpoint event remains at the same sequence. It rejects a shorter history or replacement of that anchored prefix. Without an independently retained checkpoint, a consistently rewritten history or valid tail truncation can be indistinguishable from legitimate history. Checkpoints are unsigned JSON and inherit the trust of their storage location.

## 10. Separation of concerns

Raw content → typed object → declared lineage → explicit intent → admission receipt → bounded operation → evidence object → execution receipt.

Content can influence a future reasoning system, but it cannot grant authority in this implementation. A receipt states what this local harness recorded and can replay. It does not prove a model understood an instruction, prove remote execution, or certify a source's truth.
